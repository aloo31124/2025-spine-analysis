## 一、核心設計概念（先講清楚邏輯）

* **User 採單一表 + 角色欄位**
* **店長 ↔ 操作員** 使用「父子關係（self-reference）」
* **商品永遠只綁一個 userId（建立者）**
* **營收/銷量計算靠「登入者角色 + user 關聯」動態查詢**
* **操作員無法查趨勢 → 用 RBAC 控制，不靠資料表硬擋**

---

## 二、ER 圖（文字結構）

### 1️⃣ User（使用者）

```
User
-------------------------
id (PK)
role              ENUM('MANAGER','OPERATOR')
parent_user_id    FK -> User.id   (nullable)
name
email
created_at
```

#### 關係說明

* `MANAGER`

  * `parent_user_id = NULL`
* `OPERATOR`

  * `parent_user_id = 店長.id`
* **一位店長（User）**

  * 可以擁有多位操作員（User）

```
User (MANAGER)
  └── User (OPERATOR)
  └── User (OPERATOR)
```

---

### 2️⃣ Product（商品）

```
Product
-------------------------
id (PK)
user_id           FK -> User.id   (建立者)
name
price
status
created_at
```

#### 規則對應

* 店長建立商品 → `user_id = 店長.id`
* 操作員建立商品 → `user_id = 操作員.id`
* **商品不直接綁店長**
* **營收統計靠查 user 關聯**

```
User 1 ────< Product
```

---

### 3️⃣ Order（訂單）

```
Order
-------------------------
id (PK)
product_id        FK -> Product.id
quantity
total_amount
created_at
```

```
Product 1 ────< Order
```

## 四、營收 / 銷量計算邏輯（關鍵）

### ✅ 當登入者是【店長】

**可計算的 userId 範圍：**

```
自己 + 所有 parent_user_id = 自己.id 的操作員
```

SQL 概念：

```sql
SELECT SUM(o.total_amount)
FROM orders o
JOIN products p ON o.product_id = p.id
WHERE p.user_id IN (
  SELECT id FROM users WHERE id = :managerId
  UNION
  SELECT id FROM users WHERE parent_user_id = :managerId
);
```

---

### ❌ 當登入者是【操作員】

* **API 層直接擋**
* **不回傳趨勢資料**
* 不靠資料庫權限判斷（避免業務邏輯分散）

---

## 五、為何這個 ER 設計是「正解」

### ✅ 優點

* ✔ 商品歸屬清楚（誰建誰負責）
* ✔ 不需要在 Product 存 `manager_id`（避免重複欄位）
* ✔ 支援未來：

  * 多層級角色
  * 區域店長
  * 多品牌
* ✔ SQL 聚合邏輯簡單

### ❌ 不推薦的設計

| 錯誤做法                               | 問題       |
| ---------------------------------- | -------- |
| Product 同時存 operatorId + managerId | 資料冗餘     |
| 營收表硬存 managerId                    | 無法動態調整組織 |
| 用 boolean 權限欄位                     | 擴充性差     |
