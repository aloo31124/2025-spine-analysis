  > ✅ 已定義：FR-007 要求拒絕操作，User Story 6 驗收條件明確要求提示「操作員未綁定店長」
- [x] CHK008 - 「商品創建流程響應時間不增加超過 200ms」的測量基準是否明確？ [清晰度, Spec §SC-006]

- [x] CHK009 - 「清楚標示該操作員屬於當前店長」的視覺呈現方式是否定義？（顏色/圖示/文字標記） [清晰度, Spec §FR-014]

- [x] CHK010 - 舊資料遷移的執行時機與方式是否明確說明？ [清晰度, Spec §Assumptions]
  > ✅ 已說明：Assumptions 明確舊資料 createId=userId, lastEditId=createId, lastEditTime=createDate，屬實作指引

## 權限控制需求 (Permission Control)

- [x] CHK015 - 操作員身份驗證的時機是否明確？（創建前/API 層/服務層） [完整性, Spec §FR-001]
  > ✅ 已明確：FR-001 明確要求「處理商品創建請求時」檢查，plan.md 明確實作於 Service 層（遵循分層架構）
- [x] CHK016 - 操作員權限範圍是否明確界定？除了商品創建外還有哪些操作？ [完整性, Gap]
  > ✅ 已完整界定：FR-008~FR-013（查看+編輯所屬店長所有商品），FR-040~FR-043（無刪除權限），Assumptions 明確說明
- [x] CHK017 - 店長對操作員創建商品的編輯/刪除權限是否明確定義？ [完整性, Spec §User Story 2]
  > ✅ 已定義：FR-013（店長可編輯所有歸屬自己的商品），FR-041（店長可刪除），User Story 5 驗收條件明確說明
- [x] CHK018 - 操作員是否可編輯/刪除自己創建的商品？此權限是否有定義？ [Gap]
  > ✅ 已定義：FR-011（操作員可編輯所屬店長所有商品，包括自己創建的），FR-040~FR-042（操作員無刪除權限，即使自己創建的也不可刪除）

## 資料完整性需求 (Data Integrity)

- [x] CHK019 - createId 欄位的資料型態與約束是否定義？（必填/可為 null/外鍵關聯） [完整性, Spec §Non-Functional]
  > ✅ 已定義：Key Entities 定義為 String 類型，Data Integrity 明確為「必填（操作員創建時）或可為 null（舊資料相容）」

  > ✅ 已說明：Data Integrity 要求「透過資料庫約束或應用層驗證確保一致性」，FR-004~FR-006 定義邏輯規則
- [x] CHK021 - 商品編輯時 createId 不可修改的約束是否有技術實作說明？ [完整性, Spec §Out of Scope]
  > ✅ 已說明：FR-014 明確要求不可修改，Security 要求「僅創建時寫入，後續不可修改」，Out of Scope 排除修改功能
- [x] CHK022 - 操作員帳號被刪除後，createId 的處理方式是否定義？ [Gap, Open Questions]
  > ✅ 已定義：Edge Cases、Clarifications (2026-01-28)、Assumptions 明確要求保留 createId 不變，FR-044 要求前端顯示「已離職用戶」標記

## 邊界情況與例外處理 (Edge Cases)

- [x] CHK030 - 操作員被解除綁定後的商品歸屬是否明確說明？ [完整性, Spec §Edge Cases]
  > ✅ 已明確：Edge Cases 明確「已創建的商品仍歸屬原店長，createId 和 lastEditId 永久保留不變」，Clarifications (2026-01-28) 補充詳細說明
- [x] CHK031 - 操作員重新綁定至不同店長的處理邏輯是否清晰？ [清晰度, Spec §Edge Cases]
  > ✅ 已清晰：Edge Cases 明確「之前創建的商品仍歸屬原店長，新創建的商品歸屬新店長；操作員僅可編輯當前綁定店長的商品」
- [x] CHK032 - 店長帳號被停用/刪除時商品的處理方式是否有決策？ [Gap, Spec §Edge Cases]

- [x] CHK033 - 操作員同時擁有多重角色時的優先順序是否定義？ [清晰度, Spec §Edge Cases]
  > ✅ 已定義：Edge Cases 明確「系統應優先檢查是否為操作員，若是則套用操作員邏輯」

## 使用說明

1. 逐項檢查規範文件，確認該需求是否已明確定義
2. 通過項目標記為 `[x]`
3. 發現問題時在項目下方新增註解說明
4. 標記為 `[Gap]` 的項目表示規範中可能缺少該定義
5. 所有 `[Gap]` 項目應回報給規範撰寫者進行補充

## 標記說明

- **[完整性]** - 檢查需求是否完整涵蓋所有必要資訊
- **[清晰度]** - 檢查需求描述是否明確無歧義
- **[一致性]** - 檢查需求之間是否相互一致
- **[Gap]** - 標示規範中可能缺少的定義
- **[Spec §X]** - 引用規範文件中的相關章節
